# ADR-0001: LS as the relay between GitHub and CS

Status: Accepted (2026-10)

## Context

CS sits on a private network and has restricted access to sites outside the country. GitHub can't call into CS. LS (a Linux machine with systemd, or WSL2 on Windows) has unrestricted internet and reaches CS over VPN/LAN.

## Decision

Everything that needs internet (pulling images from GHCR, downloading build dependencies, reading GitHub) runs on LS. CS only receives images from the internal registry (`CS_REGISTRY` in `common.env`) and is controlled through the Dockhand API that LS calls (a pull/push-from-inside model, no inbound port opened).

## Consequences

- No inbound port needed on CS, no tunnel.
- LS is a single point of failure for build and deploy. If LS is off, containers on CS keep running; CS keeps 2 images so a manual restore via Dockhand is possible.
- Work can't be shifted to CS since CS has no outbound internet.
- Reduced risk by: disabling sleep/suspend, disabling network-card power saving, a self-restarting service (ADR-0009). Plain Linux has fewer failure points than WSL2. A second standby machine is only worth it if downtime causes real damage (two bots sharing a token would fight over commands, so only one runs at a time).

## Alternatives considered or deferred

- A self-hosted runner inside the network (an office Mac Studio): free runner minutes, but GitHub once announced then deferred a $0.002/minute charge; the Mac is arm64 while the server is amd64 (Jib needs `quarkus.jib.platforms=linux/amd64`, Dockerfile builds need amd64 too). Shelved.
- An inlets-style tunnel from a GitHub runner into the private network: still needs a public endpoint and a license.
- Jenkins: see ADR-0011.
